## M0 讀碼結論（影響實作的關鍵事實）

- `EngineStepper.applyData()` 每個 canonical tick 都會產出一個 `DescriptorFrame`（缺測 tick 也產出，`validityMask = false`），
  且已經在 `StepResult.emittedDescriptor` 帶出來——參與統計可以直接掛在這條路上，不必動描述子管線。
- 「是否在評分段內」＝`StepResult.activeSegment != null`（`ReferenceTimeline.segmentAt(videoTimeMs)`）。
  `applyData` 只有在 `isRunning && !isPaused && playbackRate ≈ 1` 時才 resolve segment 並餵 Aspect，參與統計沿用同一個 `active` 判定。
- 缺測來源有三種，都要當缺口：`CanonicalImuSample.missing`（≥3 tick 沒資料，`validityMask = false`）、
  `gapBoundary`（epoch 重啟或缺口後第一筆）、以及時戳不連續（回放端以 `Seek` 重錨）。
- `stillnessProbability` 由 `DescriptorSequencer` 以 `motionEnvelope`（2 m/s² 尺度）與角速度（1 rad/s 尺度）取小值算出，
  §0-C 的靜止門檻 0.70 直接可用。
- 節奏規律性可重用 `TempoAspect` 的 ACF 正規化峰值算法（`autocorrelation` / `normalizedAcfPeak`），但 `TempoAspect`
  是私有實作且綁 `MafSegment`；決定在 `ParticipationTracker` 內自帶一份最小 ACF（同公式），**不改 `TempoAspect`**，
  以確保「不改五條 Flow 與三面向的行為」。

## 遇到的問題與我的決定（契約未定義處）

1. **參與統計的時鐘用 monotonic session event time，不用 `frame.timestampMs`（影片時間軸）。**
   理由：`ImuCsvReplay` 與 Player 都會在時戳不連續時發 `Seek` 重錨，若直接用影片位置相減，
   真實錄製的 230 次時戳倒退會讓 `expectedMs` 亂跳。改用 `EngineState.sessionEventTimeMs`
   （`maxOf` 單調遞增）後：倒退 → `dt = 0` 不重複累積；往前跳（真實 BLE 斷裂）→ `expectedMs` 照加、
   `measuredMs` 不加，覆蓋率如實反映斷裂（§9.4 V6 要的行為）。
2. **`activeExitMs` 補進 `ParticipationConfig`**（§9.2 提到但 §9.3 的 snippet 沒有），預設 ＝ `pauseToleranceMs`。
   另補四個 §9.3 未列的參數：`snapshotIntervalMs`（1000）、`canonicalRateHz`（25）、
   `regularityMinPeriodMs`（400，＝ ACF 搜尋帶上限 2.5 Hz）、`regularityMinPeriodicity`（0.40，與 §0-C
   periodicity 閘門下緣對齊）。全部有預設值，不影響 §9.3 的呼叫形式。
3. **遲滯的 0.5 s 候選時間會回補進 `activeMs`**（不是丟掉），否則每次重新起動都少算 0.5 s。
   候選期間若出現靜止樣本即歸零 —— 這正是 V1 白噪音 `activeMs` = 0 的原因。
4. **連續區間長度 ＝ 「最後一筆活動樣本 − 區間起點」**，所以區間尾端未超過容許的停頓不會被算進長度，
   而區間內部的停頓自然計入（§9.2 要求）。進行中的區間若已比所有已結算區間長，快照就直接顯示它
   （`longestRunMs = max(已結算, 進行中)`），使用者不必等 stop 才看到。
5. **非評分段的時間也計入「連續靜止」**：超過 `pauseToleranceMs` 的過場（INTRO／REST 等不在 payload 的段）
   會切斷連續活動區間。§9.1 只說非評分段不累積 `activeMs`，沒說區間是否切斷；判定「跨過一段沒在評分的
   過場還算同一段連續活動」對使用者是不實的，故切斷。
6. **短缺測（≤ `gapMs`）的處理**：§9.2 說「超過 `gapMs` 才視為缺口」，所以缺測時間先掛帳，
   在超過 500 ms 前恢復就補回 `measuredMs` 且不切斷區間；一超過就整段作廢並切斷（掛帳不會事後補回）。
7. **`rhythmRegularity` 自帶一份最小 ACF，不改 `TempoAspect`。** `TempoAspect` 的 ACF 是私有實作且綁
   `MafSegment`／`tempoReference`；為了守住「不改三面向行為」，`ParticipationTracker` 內自帶同公式的
   `autocorrelation` + 正規化峰值（8 s 滾動 tumbling 窗、搜尋帶 400 ms–窗長/3、窗內至少 3 個週期）。
   合格窗以時間加權平均，沒有合格窗就 `null`。

### Codex 對「59.2 s」的判斷（我接受）

不是 `resolveSegment` 每分鐘切段，而是**錄製時戳的缺口位置**：mike 在 180.907–240.126 s（59.219 s）、

|---|---|---|---|
| 7 | 嚴重 | `stop()` 用 `participation.first { it.settled }` 判斷結算完成，但 `settled` 認不出「哪一次」Stop。同一個 loop 連跑第二堂課時（`controlChannel` 是 UNLIMITED，`send` 不掛起），`first` 會立刻收下**上一堂**的已結算快照 | `EngineLoop.stopAndSettle(videoTimeMs)`：先在 `stopAcks` 佇列排一個 `CompletableDeferred`、再送 `Stop`，迴圈處理到那個 `Stop` 時才 `complete(result.participation)`。每次 Stop 有專屬回覆，FIFO 配對 |
| 8 | 中等 | 逾時（`withTimeoutOrNull` 2 s）會把未結算的舊快照當成成功結果回傳，違反新 API「返回即最終成果」的承諾 | 移除逾時。改由「迴圈結束就把待回覆以 `null` 收尾」保證不會無限等待：`start()` 的 `finally { failPendingStopAcks() }`、`EngineLoop.stop()` 也呼叫它、`stopAndSettle()` 在鎖內看到 `terminated` 就直接回 `null`。`ScoringEngine.stop()` 拿到 `null` 時回傳 `settled = false` 的當下值，文件明寫「`settled = false` 代表沒有結算，不要當成課程成果」 |

順手把主迴圈兩處控制事件處理收攏成 `applyControl(control)`（頂端排空迴圈與 `select` 分支共用），
控制優先於資料的結構不變。並在 KDoc 註明**不支援並行 `stop()`**（回覆是 FIFO 配對）。

### 新增測試

| 測試 | 內容 | 結果 |
|---|---|---|
| 同一個 loop 連跑第二堂課 | `start(0)`／無樣本／`stop(10_000)`；接著 `start(20_000)`／`stop(50_000)` | 第二次回傳 `settled = true`、**`expectedMs` 30,000**（不是第一堂的 10,000） |

## M3 第三輪 Codex QA（09:40，最後一輪）：`stop()` 握手再修 2 項

Codex 確認 FIFO 回覆配對、鎖內的 `terminated` 檢查、`applyControl` 重構、世代守衛都正確，
但在 `stop()` 的失敗路徑又找到兩個（原始輸出 `handoff-d2/qa-core-3.txt`）：

| # | 嚴重度 | 缺陷 | 修正 |
|---|---|---|---|
| 9 | 高 | `launch { try { runLoop() } finally { failPendingStopAcks() } }`——`launch` 的本體**可能在被排程執行之前就被取消**，那時 `finally` 整段不會進去，`terminated` 留在 false，已入列的回覆永遠等不到人完成（`ack.await()` 死等） | 改成 `scope.launch { runLoop() }.also { it.invokeOnCompletion { failPendingStopAcks() } }`；`failPendingStopAcks()` 本來就冪等 |
| 10 | 中 | `stopAndSettle()` 回 `null` 時，`ScoringEngine.stop()` 退回 `_participation.value`——那可能是**上一堂課已結算**（`settled = true`）的快照，呼叫端會把舊成果當成這次的結果 | `null` 路徑一律回傳 `ParticipationSnapshot.EMPTY`（`settled = false`、全 0），不沿用公開快照；`loop == null` 的早退也改成 EMPTY。KDoc 與 SDK 文件同步說明 |

第三輪已是計畫允許的最後一輪；這兩項修正各只有一兩行、語意單純（讓失敗路徑誠實），
不再開第四輪，改以既有測試（`release()` 之後 `stop()` 回傳 `settled = false` 且 ＝ EMPTY）覆蓋。
